# UnifiedMining

J6B 的三项弯道、四项静止起步指标同时检查普通前车 TTC 和 cut-in TTC，
任一路有效 TTC `<4.5s` 即截断/终止候选；等于 4.5s 允许，无有效 TTC 时保持原行为。
五项跟车刹停指标允许同一目标 ID 在普通前车与 cut-in 状态之间连续切换；
目标 ID 改变或丢失立即截断，未完成刹停的旧片段不计有效 Case，新目标独立重新筛选。
跟停 TTC 测量使用普通前车/cut-in 的有效最小 TTC，刹停反应保持首次自车减速取值及 3.5s 阈值，
刹停风险保持整段最小 TTC 及 1.5s 阈值；距离的刹停后 2s 窗口也允许同 ID 状态切换。
其他跟停门控、指标数值阈值及 MMT 均不变；Bad Case 图独立展示 cut-in TTC，判定曲线与指标取值一致。

有前车点刹场景要求自车全程 `>=30km/h`、前车绝对速度全段极差 `<=4km/h`，
并在场景起点、终点分别检查前后各 1s 的前车速度，窗口极差须 `<=0.5m/s`。
边界窗口数据不足、前车无效或速度非有限值时排除场景；有前车场景不再桥接基础条件间隙，
避免将低于 30km/h 等失效帧纳入。原稳定跟车的距离、相对速度、稳定时长等门控仍保留；
无前车点刹场景及制动脉冲判定阈值不变。

独立“ABS激活”统计项（`abs_activation_count`）已删除，不再挖掘或导出。
保留“ABS触发关联ACC退出”（`acc_exit_after_abs`）及其依赖的 ABS 信号。

“跟车刹停反应”（`follow_stop_ttc`）在原跟停场景内，取首次自车原始纵向加速度
`<=-0.5m/s²` 且 TTC 有限时的 TTC，不再取整段最小 TTC；`TTC>=3.5s` 合格。
不要求前车加速度触发，不平滑加速度、不附加持续时间确认。
没有有效取值点时不判 Bad，保持原总 Case 计数；Bad Case 图仅将实际取值点作为超限证据。

这是新的统一 H5 数据挖掘框架。Raw 目录只作为历史逻辑参考，新入口不调用 Raw 代码。

## 运行

```bash
python3 DataMining.py
```

Windows 环境如果没有 `python3` 命令，用 `python DataMining.py` 等价运行。程序会自动读取同目录下的 `config.json`。

输出在 `UnifiedMining/Result_Test`：

- 每个指标一个 CSV
- 每个指标一个 `_events.json`
- `skipped_metrics.csv` 记录因缺失信号而未运行的指标，包含指标名称、文件路径、缺失字段和缺失 H5 路径
- 一个汇总 XLSX 报告，汇总页和明细页都会标注 `指标类型`：CPI 或 MPI
- `run_manifest.json` 记录本次输入和指标列表；`failed_h5_files` 记录读取失败后跳过的 H5，`complete=false` 表示结果不完整
- H5 打开失败时默认重试 2 次、间隔 2s（`defaults.h5_read_retries` / `defaults.h5_read_retry_delay_s`）；仍失败则跳过该文件，且不与前后文件拼接
- `lcc_activation_sync.png` / `lcc_activation_sync.json`：启用 `lcc_sync_check`（默认 true）时生成 LCC 总线/ETH 同步诊断，
  使用本次挖掘经过路径及日期筛选的文件和两路原始报文时间戳。开启/退出任一匹配边沿的绝对时间差
  严格大于 200 ms 判为有较大延迟；等于 200 ms 不计超限。无有效样本时结果为“否”并明确注明原因，
  不代表已验证同步正常。GUI 任务队列显示是/否和结果图链接，不改变 CPI/MPI 统计。
  沿用独立检查的同向最近边沿匹配，最大窗口 ±10 s，不跨文件配对，不自动校准时间轴。
  命令行直接挖掘时在所有挖掘报告及信号图完成后执行；GUI 通过内部 `lcc_sync_deferred=true`
  将检查移至自动对比报告之后，作为独立任务运行，结果回填原 J6B 行。
  关闭 `lcc_sync_check` 不读取延迟信号、不生成诊断文件，原有指标及报告照常输出。
  需要 Pillow 及 Windows 中文字体；检查异常显式报错，已经生成的报告保留。
  支持根目录和单层采集文件包装目录下的候选路径直接定位；未命中时仅沿
  `ch*/网络/DBC/目标报文/signals` 查找五个 LCC 相关报文，不递归扫描整棵 H5 树，
  不打开无关报文、信号或 Topic 分支。实际选中的两路信号路径会写入日志。
  多候选优先级评分最多读取前 50000 个采样，出现最高优先级合法枚举后立即停止评分；
  单候选不重复评分读取。HDF5 读取异常按文件记录原因并继续处理剩余文件，
  保留已完成的统计及结果图；JSON 的 `read_errors` 记录文件、异常类型及原始错误。
  只要存在读取失败，队列显示“检查不完整”或“是（结果不完整）”，不能当作正常的“否”。

`bad_case_report.xlsx` 的“指标名称”使用与对比报告一致的中文名称，
另保留“指标Key”列用于追溯和曲线绘图。配置、CSV/JSON 文件名及汇总报告代码名保持不变。
“行车-无干扰加速”的全部 12 项指标不导出至 Bad Case 报告（也不生成该报告中的信号图），
但继续正常计算并保留 CSV、事件 JSON、汇总报告及对比报告中的统计。

Bad Case 关键信号图按信号拆分独立子图与纵轴：车速/设速/弯道限速、前车距离/TTC/前车速度、
各驱动/制动扭矩、坡度/曲率、各状态位、四轮方向/挡位/轮速分别展示，
不因单位或量级不同而压缩在同一纵轴。仅原始加速度与其 0.3 秒平滑曲线保留同轴对照。
每个子图预留固定可读高度，整张 PNG 随子图数增高，保留原有阈值及关键时刻标记。
TTC/限速不再为显示而截到 120；曲率直接使用 1/m 单位，不再乘 1000。
Excel 内仍为缩略图，查看数值和分布请使用报告中的完整 PNG 链接。
挖掘汇总报告的“指标名称”右侧新增“中文指标名称”列，原代码名和统计口径保持不变。

### Bad Case 信号图（可选）

在 UnifiedApp 的 J6B 运行参数勾选“信号图”，或在挖掘配置设置
`"bad_case_signal_plots": true`（默认 false），挖掘结束后会读取原始 H5，
在本次 `bad_case_report.xlsx` 右侧增加“关键信号图”和“绘图状态”列。
绘制范围为 `bad_case_extract.json` 筛选后保留的 Case，不是全部原始事件。
关闭开关时不读取 H5 绘图，不额外生成图片；Bad Case 提取未启用时日志会提示跳过。

- 数值型 CPI 保存本次动力形式下实际使用的筛选上下限、判定值和关键时刻，
  图中显示筛选阈值线、越界红点和关键时间竖线；粉色背景仅表示事件窗口，
  不表示窗口内每一帧都越界。jerk 与挖掘统一使用下述持续 jerk 算法。
- 加速度和 jerk 分开绘图、分别标注单位；加速度同时显示原始值与 0.3 秒平滑值。
- 时间、平均值及波动等统计量显示为“事件统计值，非瞬时曲线”，
  并配套展示实际速度、加速度等上下文信号，不将统计量伪装成瞬时测量值。
- 事件型 MPI 标出已识别的事件时间段；ABS/TCS/VSE 关联退出等有关键时刻记录的指标
  另标激活、退出等时间点。组合条件与原始判定数据保留在“问题内容”和“判定数据”列，
  不虚构通用数值越界阈值，也不把准出阈值作为事件筛选阈值。
- 信号缺失时不绘制默认零曲线。单条读取/绘图失败会在对应行和日志明确显示，
  其余 Case 继续生成；报告保存失败仍抛出错误。
- Excel 内嵌缩略图，完整分辨率 PNG 保存在报告同目录的
  `<报告名>_signal_plots` 文件夹；“绘图状态”中的链接可打开高清图，
  分享高清图时需要同时保留图片目录。增加绘图会提高耗时及报告体积。
- 旧报告若未保存“判定数据”，仍可单独补画事件窗口和上下文信号，
  但无法还原当时未记录的数值阈值及精确判定点；需重新挖掘以获得完整证据。

绘图环境需要 Pillow、openpyxl、numpy、h5py，以及中文字体。
Ubuntu 可使用 Noto Sans CJK 或文泉驿字体；该功能当前仅接入 J6B，不改变 MMT。

## 结构

- `DataMining.py`：唯一主入口，负责加载配置、发现 H5、加载 filters、生成报告。
- `config.json`：统一配置。`signals` 是标准字段名到 H5 显式路径的映射；
  `powertrain_type` 必填，可设为 `ICE`、`PHEV` 或 `BEV`，用于选择动力形式对应的 CPI 阈值。
- `signal_preprocessor.py`：统一信号预处理，读取 H5、按时间轴采样、生成衍生字段。
- `metric_utils.py`：公共工具函数库，包含 Metric 数据结构、分段、采样后计算、jerk/TTC/严重度等可复用工具；具体指标逻辑不放在这里。
- `reporting.py`：CSV、JSON、XLSX 输出。
- `filters/`：每条指标一个筛选文件，指标类型、阈值、场景选择和 `evaluate` 逻辑都落在对应文件里。

## CPI / MPI

指标类型不是 H5 数据来源拆分，而是指标自身分类：

- CPI：纵向场景/体验类指标，例如跟停、跟起、坡道、曲率限速。
- MPI：状态/执行/请求类指标，例如 ABS/TCS/VSE 激活、ACC arbitration、重制动、顿挫、溜车等。

代码里每个 Metric 都带 `category` 字段；报告里用 `指标类型` 列标明 CPI/MPI，不拆成两份报告。

控制抖动和跟车刹停波动指标已移除，不再加载、挖掘或输出报告。
点刹保留原挖掘逻辑，版本对比报告中的准出标准在三种动力形式下统一为 MPI ≥80。

汇总页固定使用一列 `指标值`：

- CPI 指标沿用原口径：无 Bad Case 时显示 `100.0(总Case/Bad Case)`，有 Bad Case 时显示 `总Case / Bad Case`。
- MPI 指标使用里程归一化口径：`指标值 = 当前统计数据总里程 km / 总Case数`，显示为 `x.xxxkm/case(总里程/总Case)`。

新增的 `acc_exit_after_abs`、`acc_exit_after_tcs`、`acc_exit_after_vse` 三个 MPI，
分别统计 ABS/TCS/VSE 激活与 ACC 退出的时序关联：功能从未激活变为激活时 ACC
须处于激活状态，且 ACC 在随后 1 秒内从激活变为未激活。每次 ACC 退出每个分项最多计一次；
该规则表示时序关联，不等同于已证明因果。事件明细包含功能激活时间、ACC 退出时间和时间差。

### 弯道稳速与坡道稳速的连续性

弯道稳速、坡道无前车稳速均按每帧场景条件严格连续分段，不再桥接条件不满足的短暂间隙。
即使只有一帧不满足，也立即结束当前段；恢复满足条件后另起一段，失效帧不参与指标计算。
每段独立检查原有长度要求：弯道至少 50 帧且至少 5 帧曲率大于 0.004，
坡道按下面的稳速进入规则确认后持续至少 5 秒。不将间隙两侧长度合并。
此变更仅针对上述两类场景，不改变其他事件指标的合并规则或 MMT。
弯道稳速逐帧排除有限 TTC `<4.5 s` 的采样，等于 4.5 秒允许；无有限 TTC 不因此排除。

### 坡道稳速进入规则（J6B / MMT）

坡道控速稳定性、坡道控速舒适性、坡道稳速抖动三项共用稳速场景。
在各平台原有坡道、无前车、功能激活等基础条件持续满足时，要求有效且正值的
SetSpeed 保持不变（相对当前候选段首值容差 `1e-6`），车速连续至少 1 秒位于
SetSpeed ±2 km/h（含边界），从确认满 1 秒的当前采样点开始统计，确认前的数据不计入。
J6B 的车速为 m/s、SetSpeed 为 km/h，比较前换算单位；
MMT Topic 的底盘车速和 UNP `cruise_velocity` 均按 m/s，进入带宽换算为 `2/3.6 m/s`。

进入后的速度离开 ±2 km/h 带仍计入，用于检出真正的稳速波动；原有基础条件失效或
SetSpeed 改变立即截断，不桥接间隙，恢复后重新等待 1 秒。每个确认后的稳速段至少 5 秒，
即一段从一开始就位于进入带内的数据至少需覆盖 6 秒。不再要求 MMT 段内车速跨过 SetSpeed−0.5，
也不再使用其 20 帧坡度恢复例外；保留各平台其他基础条件。
MMT 三项统计均使用完整的确认后稳速段，不再按仪表车速进行二次裁剪。
本次只统一场景，原有加速度、jerk、车速波动的计算公式、单位及 Bad Case 阈值不变。

### stop2go 起步场景

跟车起步舒适性（`follow_start_jerk`）取消 1.0 m/s³ 下限，仅检查最大 jerk ≤2.0 m/s³，
含上限边界；低于 1.0 不再判 Bad Case 或计严重度。跟起场景及 jerk 计算方法不变。

起步加速建立时间不再限制最小 1 秒，仅检查上限：ICE ≤4.5 秒，PHEV/BEV ≤4.0 秒，
含上限边界；计算方式仍为首次加速度 >0.2 m/s² 到场景最大加速度的时间差。
小于 1 秒（包括可计算的 0 秒）不因建立过快判 Bad Case。其他起步指标阈值不变。

四项起步 CPI 共用同一场景：从“上一帧静止、当前帧运动且 ACC 激活”开始，
起点及后续每帧均检查以下条件，与 MMT 的加速度、SetSpeed 和 TTC 检查对齐：

- 原始纵向加速度（`acceleration_total`，不做坡度补偿）有限且 `>=0 m/s²`；
- SetSpeed 有限、与上一帧差值 `<=1e-6 km/h`，自车车速不超过 SetSpeed（比较前统一单位）；
- 有限 TTC 不得 `<4.5 s`，等于 4.5 秒允许；无有限 TTC 不因此排除。

新增条件失效时终止当前段，失效帧不纳入计算；条件恢复后不会从行驶中重新开启场景，
仍须新的静止到运动转换。缺少加速度或 SetSpeed 时按缺信号跳过，不填默认值。
仍保留 J6B 原有 ACC/曲率限制、达到 8 m/s 截止、场景至少 5 秒和峰值车速至少
10 km/h 的要求，不改成 MMT 的 50 帧长度或其红灯/直道筛选。

### 跟车刹停距离

保留原跟停场景识别和动力形式筛选阈值，但不再使用刹停首帧距离。设原场景刹停时刻为
`t0`，完整观察 `[t0, t0+2s]`，取 `[t0+1s, t0+2s]` 内前车距离的中位数作为判定值。
距离仍直接使用 `FLT1_Long_Range`，不新增车长/车头偏移补偿；ICE 合格区间为
`[2.5, 4.5] m`，PHEV/BEV 为 `[3, 4] m`，含边界。

完整观察期间要求自车持续静止、ACC 激活、同一有效前车目标持续存在、前车绝对速度
不超过 0.2 m/s，距离有限且为正。观察需完整覆盖 2 秒，采样间隔不能超过 0.2 秒；
最后 1 秒至少有 3 个有效采样。窗口右边界没有恰好采样时，以紧邻其后的采样确认覆盖和状态，
但不将边界外距离加入中位数。数据不足、自车/前车起步、目标切换/丢失等场景不计入有效总 Case，
原因写入指标明细；不回退首帧或缩短窗口。连续的下一 H5 可提供观察数据，不连续或缺口过大则排除。

Bad Case 事件延长到观察结束，判定数据保存刹停时刻、稳定取值区间及样本数。
信号图标出取值区间，中位数显示为事件统计值，另保留前车距离曲线，不把中位数伪装成某帧距离。
“稳定值”在此指末段中位数，不额外引入距离方差或极差门槛。

### 持续 jerk 计算口径（J6B）

所有基于加速度计算的 jerk（CPI、顿挫/重制动 MPI、Bad Case 信号图及扭矩顿挫复核图）
统一先对原始纵向加速度做 **0.3 秒居中时间窗算术平均**，再在 **0.3 秒居中时间窗**
内按真实采样时间进行多点最小二乘直线拟合，斜率即 jerk，单位 `m/s³`。
不再对相邻采样点做差分，也不对结果额外二次平滑；保持原有 jerk 阈值和事件持续时间条件。
“持续”指窗口内的变化趋势，不表示新增“越界必须持续 0.3 秒”的条件。

文件边缘使用截短的时间窗。拟合至少需要 3 个有限值，且有效采样时间跨度至少 0.15 秒；
不足时输出 NaN，表示无法测量，不用零值或两点差分补齐。时间轴非有限或非严格递增时明确报错。
实现采用分块局部时间原点，避免长记录或大时间戳导致拟合数值精度下降。

MMT 已同步使用相同的持续 jerk 算法。不修改其他独立统计量的平滑窗口（例如无干扰加速的 0.5 秒窗口，
以及扭矩顿挫高频加速度分析的 0.12/0.8 秒窗口），也不修改扭矩变化率的计算。
新旧算法可能得到不同的峰值、Bad Case 数和严重度；版本比较应使用新算法重新挖掘双方数据。
旧报告保存的判定值不自动更新，不能只补图就当作新口径的挖掘结果。

### 行车-无干扰加速 CPI

`driving_uninterfered_accel_*` 指标按初始车速分为 `0–30`、`30–60`、`60–90`、`90+ km/h`
四档，每档分别统计最大加速度、加速建立时间和平均加速度 CPI。入口条件连续满足
0.5 秒后，以满足条件的第一帧为起点；ACC 必须激活且无 override、前车或 cut-in，SetSpeed
至少高于当前车速 22 km/h，且曲率限速未介入或高于目标车速 2 km/h。事件期间任一条件失效、
出现超过 0.2 秒采样间隔、30 秒内未增加 20 km/h，或平滑车速相对峰值下降超过 1 km/h
并持续 0.5 秒时，事件不纳入统计。速度和加速度均采用 0.5 秒时间窗平滑；加速建立时间为
加速度首次超过 0.2 m/s² 至该事件最大加速度的时间，平均加速度按固定 20 km/h 增速除以
事件耗时计算。加速度使用原始纵向加速度，不做坡度补偿。

最大加速度按每段事件判定：ICE、PHEV、BEV 的全部初始车速档均采用闭区间
`1.5–2.5 m/s²`，低于下限或高于上限记为 Bad Case，严重度按越界量除以 `1 m/s²` 再乘 100。
汇总采用其他 CPI 相同的总 Case / Bad Case 展示口径，不再显示最大加速度均值。
平均加速度必须 `>1.5 m/s²`，加速建立时间必须 `<3.5 s`，等于对应边界也记为 Bad Case。
三类指标均按事件独立判定并采用常规 CPI 展示；严重度按越界量除以对应单位基准 1 再乘 100，
严格不等式边界上的 Bad Case 严重度为 0。以上标准适用于三种动力形式和全部初始车速档。
J6B 当前没有红灯/停止线信号映射，因此 J6B 版本未应用“无红灯且停止线距离大于 50 m
或无停止线”筛选；结果与应用了该筛选的 MMT 结果不完全同口径。cut-in 信号或其他必要信号
缺失时指标跳过，不把缺失信号当作无干扰。

总里程由 `VehOdo` 计算：每个 H5 文件取有效 `VehOdo` 末值 - 首值，所有文件相加。当前配置路径为 `CAN0/Vehicle_Odometer.IVehOdo`，有效位为 `CAN0/Vehicle_Odometer.IVehOdoV`；如 H5 中 `VehOdo` 不是 km 单位，调整 `defaults.odometer_scale_to_km` 即可。

## 信号路径规则

`config.json` 的输入配置：

```json
"input_path": "../Raw",
"date": "20260702-20260703",
"powertrain_type": "PHEV"
```

- `input_path` 必须是文件夹路径。
- `powertrain_type` 必须明确填写为 `ICE`、`PHEV` 或 `BEV`；本次运行选用的值也会记录在 `run_manifest.json`。
- 三类动力形式独立配置阈值：ICE 保留原 ICE 标准，PHEV、BEV 的初始值分别沿用原 PHEV/BEV 标准。
  旧配置 `PHEV/BEV` 会提示警告并迁移为 `PHEV`，纯电车辆请明确改选 `BEV`。
- 程序会递归扫描该文件夹及其子文件夹中的所有 `.h5` / `.hdf5` 文件，因此可以直接填写车型上层目录，例如 `F:\数据挖掘\DataMiningData\J6B\_Data\ES27PV011`。
- `date` 格式固定为 `YYYYMMDD-YYYYMMDD`，按闭区间过滤。程序优先读取 H5 最近一级带日期的父文件夹；父目录均无日期时，再读取 H5 文件名中的日期。
- 文件夹名和文件名中的日期均支持 `YYYY-MM-DD` 或 `YYYYMMDD`，例如文件夹 `20260827-E2LB-2-ES27PV011_parsed`，或文件 `VC9_ver0520_2026-06-25_10_50_58_CAN_parsed.h5`。
- `filters` 目录固定为 `UnifiedMining/filters`；时间轴固定使用标准字段 `acceleration`。

`config.json` 中每个 `signals` 值都必须是 H5 内的明确路径，例如：

```json
"front_range": "Eth_Debug_CAN5/Forward_Looking_Target_1.FLT1_Long_Range"
```

缺失信号按指标处理，不按整车文件处理。预处理会读取当前 H5 中存在的信号并记录缺失路径；某条指标运行前只检查自己依赖的字段，缺失时该指标在对应 CSV 中标记为 `SKIPPED`，并写出标准字段名和配置 H5 路径，其他不依赖该信号的指标继续运行。

`stationary_state` 当前读取 `CAN2/Automatic_Braking_Status_044_M.IVehMvngStat`，其中 `0` 表示 moving，`1` 表示 stationary。`stationary_flag` 使用组合规则：`ego_speed_mps < 0.01` 或 `IVehMvngStat == defaults.stationary_value` 任一成立即认为 stationary；`moving_flag` 为其反值。

纵向加速度采用 `CAN2/IMU_Yaw_Long_Acc_038_M.IIMULonAccPri`，并用 `IIMULonAccPriV` 校验有效性；`IIMULonAccPriV == 0` 表示有效。车速采用 `IVehSpdAvgDrvn_1`，并用 `IVehSpdAvgDrvnV_1` 校验有效性；`IVehSpdAvgDrvnV_1 == 0` 表示有效。无效采样点会置为 `NaN`，不会参与后续指标计算。

坡度信号配置为 `slope_deg`，当前 H5 路径是 `Eth_Debug_CAN5/MPC_DebugMsg_Reserved_18.Debug_single_Reserved_51`，真实含义是坡度角，单位 `deg`。预处理会派生内部字段 `slope_acc = 9.80665 * sin(slope_deg)`，单位 `m/s^2`，仅用于 `slope_no_frnt_acc`、`slope_no_frnt_jerk`、`slope_no_frnt_vel_fluct` 的坡道场景筛选。`acceleration_total` 直接等于 `acceleration`，不再叠加坡度。

## Cut-in 目标说明

跟车目标和 cut-in 目标使用同一套 `Forward_Looking_Target_1.*`，由 `FLT1_CUTIN_Flag` 判断当前 FLT1 的语义：

- `FLT1_CUTIN_Flag = 0`：FLT1 表示跟车目标，派生 `front_*` 字段。
- `FLT1_CUTIN_Flag = 1`：FLT1 表示 cut-in 目标，派生 `cutin_*` 字段。

当前已配置的 FLT1 显式路径：

- `front_target_id`: `Eth_Debug_CAN5/Forward_Looking_Target_1_Res.FLT1_Global_ID`
- `front_range`: `Eth_Debug_CAN5/Forward_Looking_Target_1.FLT1_Long_Range`
- `front_velocity_abs`: `Eth_Debug_CAN5/Forward_Looking_Target_1.FLT1_Long_Velocity`
- `front_accel`: `Eth_Debug_CAN5/Forward_Looking_Target_1_Res.FLT1_Long_Accel`

样例 H5 暂未找到 `FLT1_CUTIN_Flag` 的明确路径，所以 `config.json` 中 `optional_signals.flt1_cutin_flag` 当前为 `null`，预处理按 `defaults.flt1_cutin_flag_default = 0.0` 处理，即默认 FLT1 为跟车目标。拿到真实路径后，把它填成明确 H5 路径即可，例如：

```json
"optional_signals": {
  "flt1_cutin_flag": "Eth_Debug_CAN5/xxx.FLT1_CUTIN_Flag"
}
```
